## Default Outline Regeneration

An ordinary `/sp.prd <feature>` means: keep requirement facts in `prd.md`, discard the active Outline and all other Outline artifacts previously generated by `/sp.prd`, and use model reasoning to generate a fresh Outline. Missing or stale `000`/`001` project-boundary registration must never replace that job with a boundary-adoption page.

Here, ordinary means a direct full-stage invocation: not `--consume-review-confirmation`, not an explicit boundary-transition/adoption recovery route, and not a coordinator-authorized Lite scoped pass. Complete every read-only prerequisite, active-Lite, hook, and route check described below before calling reset `apply`. If any check stops or narrows the run, leave the active Outline artifacts untouched. Section order does not authorize deleting before those checks finish.

The exact `/sp.prd <feature> --consume-review-confirmation` route is not an ordinary regeneration. It exists only for the fixed loopback writer's fully `CONFIRMED` result. Do not clear or regenerate. Recompute the current Review Data ID and Outline digest, validate feature, batch, source authority IDs, source identity, owner approval, and that revision/open/draft-excluded lists are empty, then promote the current Outline to `READY_FOR_SPECIFY`. Any mismatch or non-confirmed status fails closed and returns ordinary `/sp.prd <feature>` for fresh generation; never consume a preserved archive or copied/model-authored confirmation through this route.

Before clearing anything, resolve the explicit feature and root, then run `node .specify/review/scripts/check-outline-boundary-gate.mjs specs/<root-feature>/outline-boundaries.json specs/review-index.json --feature <feature> --intent regenerate --stage prd`. Schema `speccompass.outline-boundary-gate.v1` with `allowed: true` authorizes this regeneration. `authority_status: UNREGISTERED` and `AUTHORITATIVE_BOUNDARIES_MISSING` are non-blocking advisories: finish the real Outline first and only then briefly ask whether stale boundary candidate data should be cleared and rebuilt. Never open adoption review as a substitute. A valid, human-approved structural transition, unreadable/invalid established authority, interrupted finalization, or a target excluded by an established baseline still blocks before any generated artifact is cleared. A derived index mismatch is mechanical: run the returned `sync-review-index.mjs` repair, rerun the gate, and continue only if it passes.

For any remaining `allowed: false`, leave generated artifacts untouched and return its `block_reason`, evidence, and exact `repair_command_exec`; do not invent a different repair or directly edit derived `review-index.json` identity fields.

Run `node .specify/review/scripts/reset-command-artifacts.mjs inspect prd specs/<feature>`. Accept only schema `speccompass.command-artifact-reset.v1` and keep its `inventory_digest` unchanged until apply:

Clear mode must not cite or reconstruct their decisions. Old Outline prose is never a source for regeneration in either mode.

# /sp.prd

## Outline

Goal: Create or refresh the mandatory upstream PRD intake for every new feature, capability direction, or important requirement change, while keeping `/sp.specify` as the stable requirement intake and baseline specification point.

Global rules:
- Stay within product discovery and documentation work only.
- `/sp.prd` is the mandatory upstream requirement intake. Simple requests may use a short PRD, but new feature work must not skip this stage.
- `prd.md` is the requirement-source container. The repository-root `prd/` directory is the default business-source corpus. Recursively read the files relevant to the current portfolio or child boundary. `specs/<feature>/prd.md` is the feature-local synthesis and decision writeback target; it is not the default sole source. User-confirmed, formally sourced, or consumed-decision content is a requirement fact that regenerated Outline must preserve; `[src:ai-proposed]` and `[uncertain:*]` content is not. `/sp.specify` remains the stable specification compiler for implementation-facing requirements.
- A human may name additional source directories for the repository or the current run. Add them to the default `prd/` corpus unless the human explicitly says they replace it. Never hard-code a project-specific alternate directory. Record the effective source roots and exact source anchors in `Source Authority Summary`, `Source Snapshot`, or equivalent evidence.
- Parent handoff refs, user-named files, and feature-local sources are priority reads, not an allowlist. Continue searching the authorized source roots for relevant facts and contradictions.
- Use top-down requirement growth for the PRD interview, but never copy interview headings such as goals, users, problems, scope, or process into a visible business map. Extract domain objects, actions, controls, outcomes, and boundaries before naming map branches.
- Use source tags on material content: `[src:user]`, `[src:doc]`, `[src:ai-proposed]`, `[src:user-confirmed]`.
- Use uncertainty tags when needed: `[uncertain:tbd]`, `[uncertain:assumed]`, `[uncertain:proposed]`.
- Do not write code, API routes, database schemas, framework choices, file paths, test commands, or implementation tasks.
- Do not convert `[src:ai-proposed]` ideas into confirmed requirements without user confirmation.
- Resolve low-impact, reversible design choices that do not change business scope, ownership, permissions, safety, money, compliance, irreversible behavior, or critical acceptance with model judgment; record the inference and continue. Put material boundary or business-impact decisions in the current Outline Web review as 2-4 executable options with impact and a recommendation. A model recommendation or model-authored confirmation is never human authorization.
- In headless or non-interactive runs, do not guess unclear product direction, feature boundary, human risk acceptance, or governance tradeoffs. Return `SP_STATUS: NEEDS_DECISION`, include the decision package, end with `SP_EXIT_CODE: 1`, and stop.
- User-facing next-step commands must use the host-appropriate form: `/sp.*` on slash-command hosts, or Codex skills via `$sp-*`, `/skills`, or a matching natural-language request.

Execution flow:

1. Locate the intended feature area.
   - If `.specify/memory/project-index.md` exists, read it first for project routing.
   - If `.specify/memory/active-context.md` exists, use it to avoid reading unrelated project content.
   - Resolve the effective business-source roots before drafting: use repository-root `prd/` by default, then add any human-specified directories. If a named directory does not exist or cannot be read, report that exact source gap instead of silently falling back.
   - If the target feature already exists, use `specs/<feature>/prd.md` as the PRD draft location.
   - If no feature directory exists but the user intent is clear enough to name a feature, create `specs/<feature>/` and initialize `prd.md`.
   - If even the feature boundary is unclear, ask for the macro product direction or feature boundary before writing a PRD draft.
   - In headless or non-interactive mode, do not create a guessed feature directory from unclear intent. Output a decision package with `SP_STATUS: NEEDS_DECISION`, end with `SP_EXIT_CODE: 1`, and stop.
2. Collect information through a human-friendly PRD interview structure.
   - Strategic goal: what larger product or business outcome is being pursued.
   - Product positioning: what this product or capability is, and what it is not.
   - Business goals: measurable outcomes or operational improvements.
   - Target users and roles: who uses it, who approves it, who is affected.
   - Problem domains: what problems must be solved to satisfy the goals.
   - Core scenarios: where and when the product is used.
   - Capability map: source-backed business objects, actions, controls, and outcomes grouped by cohesive product responsibility, not by PRD section headings.
   - Main flows and key branches: business flow seeds, not final flow specs.
   - Scope and non-goals: MVP boundary, excluded ideas, and why.
   - Acceptance seeds: early success checks that `/sp.specify` can stabilize later.
   - Risks and open questions: safety, data, compliance, cost, rollback, or delivery uncertainty.
3. Use model capability to grow requirements safely.
   - Preserve the user's concrete domain nouns, verbs, outcomes, root name, confirmed parent path, and explicit Outline structure before expanding or regrouping anything.
   - Propose candidate capabilities, branches, non-goals, acceptance seeds, and risks only as `[src:ai-proposed]`.
   - Compare candidates by user value, risk, cost, dependency, reversibility, and scope impact.
   - Keep rejected ideas and reasons visible so later agents do not propose them again.
   - Keep local details under their parent goal, scenario, flow, UI seed, or acceptance seed.
   - If a local detail has no parent, place it under `Open Questions`, `Candidate Requirements`, or `UI Surface Seeds`.
4. Choose the PRD depth before writing.
   - Lean PRD: use this when the user already provides a clear goal, target users, scope, and basic acceptance intent. Keep the PRD short, but still include: `Strategic Goal`, `Target Users and Roles`, `Core Scenarios`, `Scope and Non-Goals`, `Acceptance Seeds`, `Risks and Open Questions`, and `Handoff To Specify`.
   - Full PRD: use this for 0-to-1 ideas, unclear scope, multiple capability directions, governance implications, high-risk domains, or conflicting source material. Use the full section set below.
   - When unsure, prefer a lean PRD plus explicit open items instead of expanding into speculative detail.
   - Lean PRD still needs enough substance to stand on its own. At minimum it must contain one clear strategic goal, at least one target user or role, at least one bounded core scenario, explicit scope/non-goals, acceptance seeds, and at least one open question or risk when anything material is still uncertain. If those anchors are missing, treat the intake as `NEEDS_PRD` or `NEEDS_CLARIFY` instead of pretending the PRD is already sufficient.
5. Create or refresh `specs/<feature>/prd.md`.
   - Recommended sections:
     - `Strategic Goal`
     - `Product Positioning`
     - `Business Goals`
     - `Target Users and Roles`
     - `Problem Domains`
     - `Capability Map`
     - `Core Scenarios`
     - `Main Flow Seeds`
     - `Key Branch Seeds`
     - `Scope and Non-Goals`
     - `Acceptance Seeds`
     - `Candidate Requirements`
     - `Rejected Ideas`
     - `UI Surface Seeds`
     - `Data and Policy Seeds`
     - `Risks and Open Questions`
     - `Constitution Candidates`
     - `Handoff To Specify`
   - The detail boundary is: enough for `/sp.specify` to create a stable spec, not enough to skip `/sp.specify`, `/sp.flow`, `/sp.ui`, `/sp.plan`, or `/sp.tasks`.
   - The handoff result is `ready for /sp.specify`, never `ready for implementation`.
6. Create or refresh `specs/<feature>/spec-outline.md` readiness.

A model-proposed merge across conflicting authoritative identities is not admissible. If the unit has one atom, or no materially different allocation survives the hard rejects, classify the unit as `frontier` or `terminal` from its own business scope instead of claiming a decomposition.

Consider: (a) technical implementation efficiency (shared infrastructure, deployment optimization, low-latency requirements), (b) team organization (skill sets, ownership clarity, parallel development), (c) operational concerns (monitoring, scaling, failure isolation), (d) development velocity (reduced coordination overhead, smaller surface area). Ignore whether a cluster uses "generic container words" or "implementation layers" — focus on what grouping would make the system easier to build, deploy, and maintain in practice. Record this as `partition-model-architecture-unconstrained` with `approach: "unconstrained (pure architecture)"` and explain the technical rationale for each boundary. Cover every atom exactly once. You may propose fewer, larger clusters if technical benefits (shared state, reduced latency, simplified deployment) justify it, or more, smaller clusters if isolation and independent scaling matter more.

     - **Step 2 - compare, analyze, and fuse or present options.** You now have two partitions from Step 1: (A) constrained partition following SpecKit rules, (B) unconstrained partition from pure architectural judgment. Compare them across these dimensions:
       **Comparison dimensions:**
       1. **Child count**: How many children does each produce? (A: N children, B: M children)
       2. **Boundary decisions**: Which atoms are grouped together differently? Which boundaries match?
       3. **Business rationale** (from A): Does each child have a clear business responsibility and independent acceptance criteria?
       4. **Technical rationale** (from B): Does the grouping optimize implementation (shared state, deployment efficiency, team structure)?
       5. **Coordination cost**: Does B's grouping actually reduce handoffs and coordination, or does it merge responsibilities with different change drivers?
       6. **Long-term stability**: Which boundaries are stable under business evolution vs. sensitive to technical choices?
       
       **Generate comparison analysis** in `partition_comparison`:
       ```json
       {
         "constrained_count": N,
         "unconstrained_count": M,
         "agreement_boundaries": ["List atoms that both approaches group the same way"],
         "disagreement_boundaries": [
           {
             "atoms": ["atom-x", "atom-y"],
             "constrained_grouping": "Separate (rationale)",
             "unconstrained_grouping": "Merged (rationale)",
             "key_tension": "Business clarity vs. technical efficiency"
           }
         ],
         "recommended_approach": "constrained|unconstrained|hybrid|discovery_question"
       }
       ```
       
       **Decision rules:**
       Compute `disagreement_rate` using the **strict membership-change definition**: for every atom, check whether its set of co-members in the same group is identical across the constrained and unconstrained partitions. An atom counts as a "disagreement atom" if its co-member set changes in any way (either it migrated to a different group, or a neighbor migrated in or out of its group). `disagreement_rate = disagreement_atom_count / total_atom_count`. Record `disagreement_atom_count` and `disagreement_rate` in `partition_comparison`. Do not use the looser "migrated atoms only" count — a single atom's migration affects the membership of every atom in both the source and destination group, so the strict count is the correct scope of impact.
       - **If child count differs by ≤1 AND `disagreement_rate` ≤ 10%**: Auto-fuse. Adopt constrained partition for PRD structure (business boundaries remain clear), but record unconstrained partition's suggestions in `technical_implementation_notes` for later stages.
       - **If child count differs by ≥2 OR `disagreement_rate` > 10%**: Generate a Discovery question presenting both options to the human, explaining trade-offs clearly.
       - **If both approaches converge (same grouping, same count)**: Strong signal that these boundaries are correct. Adopt the partition with `high_confidence: true`.

However, when `provisional_authority` is `ai-proposed-only`, use the comparison analysis result: if auto-fused, use constrained partition as provisional; if Discovery question, present both options without pre-selecting.
       
       **Complexity consideration**: Among authority-admissible partitions, assess (a) internal complexity inside clusters and (b) coordination cost across clusters. Coordination cost is the cost of managing contracts between systems that exist as independent responsibilities. It does not justify merging two systems with different change drivers to reduce project count. Record explanations and assign `total_complexity_rank` where `1` means lowest combined cost. Split only when reduction in internal complexity clearly repays added coordination cost. Keep atoms together only when they serve one bounded responsibility and separation would add more coordination than it removes.

       **Step 4a - select a decomposition mode for each child unit.** Before naming a child, choose one primary decomposition mode from the seven below. The mode describes *why these requirements belong in one deliverable unit*, not how to implement it. Record the mode as `decomposition_mode` and explain the choice in `mode_rationale`. Other dimensions may be noted as `secondary_dimensions` but do not add extra units.

       **Seven decomposition modes:**
       - **A. Business Scenario / User Journey**: Use when the flow is complex, crosses multiple systems, or must capture a role's end-to-end path to a business result (including key exceptions and handoffs). Boundary = one role achieving one business outcome. Subject of the unit is the *user/role* ("who does what"). Example: `Strategy Submission and Approval`, `Manual Risk Review Trigger`.
       - **B. Product Feature Unit (default)**: Use when stable scope management is needed and no stronger A/C/D/E/F/G boundary exists. Boundary = one independent business capability with clear inputs, outputs, and acceptance scope. Subject is the *system/capability* ("what the system does"). Example: `Security Master Data Management`, `Multi-source Market Data Ingestion`.
       - **C. API Path / Resource**: Use when the API is the primary delivery surface and resource ownership is clear. Boundary = one resource or resource family with its business operations, permissions, idempotency, and error semantics. Merge related methods on the same resource; do not split by HTTP method. Example: `Order Resource (create, query, cancel)`.
       - **D. Data Entity Lifecycle**: Use when state, audit, compliance, versioning, or data governance matters more than page shape. Boundary = one entity's lifecycle from creation/receipt through validation, publication, change, and archive/deletion. Independent and complex state machines may become sub-entries. Example: `Market Batch Receipt and Validation`, `Quote Version Publication and Archive`.
       - **E. User Role / Permission**: Use when the same business object has materially different goals, permissions, approval responsibilities, or visible data for different roles. Boundary = one role's independent capability set within the system. Example: `Trader Order Entry and Cancellation`, `Risk Officer Review, Freeze, and Unfreeze`.
       - **F. Event / Trigger**: Use when async, scheduled, message-driven, or external-callback flows are the main delivery mode and synchronous CRUD is not the primary path. Boundary = one trigger event, processing goal, state change, side effects, and failure/retry semantics as a closed loop. Example: `Market Source Failover on Interruption`, `End-of-Day Position Valuation Trigger`.
       - **G. Integration Point / External System Boundary**: Use when the system depends on an external party (market data vendor, broker API, payment gateway, identity provider) *and* the integration's auth, protocol, rate-limiting, timeout, degradation, reconciliation, or observability needs independent design and acceptance. Boundary = one external system's complete business integration contract. A vendor name without an independent contract does not qualify; put it in `global_constraints` instead. Example: `Market Data Source Integration`, `Broker Order Gateway Integration`.

       **Granularity checks — signals the unit may be too coarse:** cannot write one unified acceptance result; contains >3 independent roles with different responsibilities; contains >2 independent state machines; Flow design needs >3 independent diagrams for this one unit; responsibility can only be described with container words like "platform/system/module/overall management". **Signals too fine:** the unit is a synonym or paraphrase of another; two units share identical trigger, precondition, role, and acceptance; the unit cannot be accepted independently; it maps directly to a single CRUD method, field, metric, state, or rule; splitting adds project count without reducing responsibility, policy, audience, acceptance, or change-context complexity.

       **Leaf-node five-question gate** — a unit may only be marked `terminal` when all five answers are "yes" with evidence:
       1. **Responsibility**: Can you write a one-sentence responsibility statement with clear subject, object, and result?
       2. **Acceptance**: Can you write 2-5 mutually independent, observable acceptance criteria? (1 criterion usually means too fine; >8 usually means too coarse; exceptions must be justified)
       3. **Flow**: Can downstream Flow produce 1-3 diagrams covering this responsibility including its exceptions and handoffs?
       4. **Source**: Is there one unique, stable, readable PRD source anchor — not just a generic section name?
       5. **Impact**: Is the change impact controllable, with the main upstream, downstream, and external dependencies identifiable?

       **Every unit must have a `project_title` following these 5 rules:**
       
       **Rule 1 - Name the unified business responsibility, not a list of objects**: The title must name the **domain and the lifecycle role** the system owns — what it governs, not what objects it holds. For multi-atom system-level projects (3+ atoms), distill a unified noun phrase from the shared lifecycle role; do NOT enumerate individual object names or list atoms separated by 、or "与". The title answers "what business responsibility does this system own?" not "what objects does it contain?". Good: 行情数据管理系统 (governs market data lifecycle), 策略研究治理系统 (governs research lifecycle). Bad: 证券身份、原始行情批次、标准行情与可信行情数据集 (this is an object list, not a system name), 外部信息原文、候选事件与可信信息特征版本 (same mistake). For single-atom projects: reuse the concrete noun of the owned business object directly. **Critical**: "复用自有对象的具体名词" means take the core noun from one owned object — it does NOT mean enumerate all objects into the title.
       
       **Rule 2 - Use industry standard terms, avoid invented abstract words**: Prefer terminology a domain expert recognizes immediately. Forbidden as primary nouns: 版本/Version, 背景/Background, 档案/Archive, 体系/System (without domain), 平台/Platform (without function), 中心/Center, 枢纽/Hub, 引擎/Engine (without context), 状态簿, 账簿. Use instead: Golden Records (not 可信版本), Decision Data (not 决策背景), Research History (not 评审档案). Good: Risk Management System (industry standard), OMS (recognized abbreviation). Bad: 外部决策背景版本 (invented abstract terms).
       
       **Rule 3 - Control length strictly**: English 2-4 words maximum, Chinese 4-8 characters maximum. Longer names indicate you are trying to encode too much information in the name; move details to `capability_summary`. Good: 行情数据管理系统 (7 chars), Market Data Management (3 words). Bad: 证券身份、原始行情批次、标准行情与可信行情数据集 (22 chars — this is a list, not a name), 订单风险与券商状态簿 (11 chars). If your title exceeds 8 Chinese characters, it is almost certainly an object enumeration rather than a system name — rewrite it.
       
       **Rule 4 - Avoid "and" / "与" / "、" connectors**: Any connector in the title means you are listing objects rather than naming a unified responsibility. This is the single most reliable signal that Rule 1 was violated. If you need "and", find the unifying upper concept: ask "What business lifecycle do these responsibilities share?" Good: 订单风控系统 (unified concept), 外部信息治理系统 (unified concept). Bad: 订单意图与风险决定 ("与" signals two objects, not one system), 宏观状态快照与市场方向强度 ("与" again), 券商交易命令、业务回报、订单生命周期与账户可交易资源 (four objects listed — name the system: 券商订单系统). **Zero tolerance: a title containing "与" or "、" fails Rule 4 and must be rewritten.**
       
       **Rule 5 - Name must be executable**: Developers should immediately envision modules and API endpoints. Test: Can you extract 1-2 entity nouns and form natural code identifiers? Good: 行情数据管理系统 → MarketDataManagementSystem, 策略研究治理系统 → StrategyResearchGovernance. Bad: 决策背景版本 → DecisionBackground? (unnatural), 证券身份、原始行情批次 → SecurityIdentityRawMarketBatch? (impossible to use as an identifier).
       
       **Naming patterns** (pick the most natural): (A) Domain + Lifecycle role: 行情数据管理系统, 外部信息治理系统, 策略研究治理系统, 交易保障系统; (B) Industry standard term: OMS, 风险管理系统, API Gateway; (C) Domain + Service: 行情数据服务, 策略执行控制.
       
       **For multi-atom projects**: Distill the shared lifecycle role into a 4-8 character noun phrase. Never enumerate atoms. **For single-atom projects**: Use the business object name directly (e.g., 持仓披露特征 is fine for a single-atom unit — but consider whether it should be merged into a larger system before naming it). Length and clarity always trump completeness — detailed responsibilities belong in `capability_summary`, not the title.

     **背景（Background）** — 1-3 sentences in plain business language explaining what the system is trying to do right now and why it got stuck. No jargon, no stage names (Stage A/B/C), no schema field names. Example: "正在把量化交易系统的27项业务能力分配到若干子系统时，发现两种分法都有合理依据，无法自动选择。"

     **影响（Impact）** — What cannot proceed until this is resolved, and what will happen if the wrong choice is made. Be specific: "如果选方案A，行情数据和外部信息会共用一个团队维护，适合小团队；如果选方案B，两个团队可以独立迭代，但需要额外定义接口合同。"

     **选项（Options）** — 2-4 numbered options. Each option must contain:
     - 选项标题（plain-language label, not "OPTION_A"）
     - 这个选项做什么（1-2 sentences of concrete action）
     - 收益（what you gain）
     - 代价（what you give up or what becomes harder）
     - 下一步命令（exact command to run after choosing this option）

     **推荐（Recommendation）** — State which option is recommended and give 2-3 specific reasons grounded in the current project's facts. Must name the concrete trade-off the non-recommended options carry. Never recommend "请您决定" or "视情况而定" as the answer.

     **确认方式（How to confirm）** — One sentence telling the human exactly how to record their choice (e.g., "在 Discovery 页面点击对应方案后保存" or "回复 `/sp.prd 000 --select partition-system-boundary-constrained`").

     Forbidden in P0 visible output: stage names (Stage A/B/C), schema field paths, atom/chain IDs, technical error traces, generic placeholders such as "请补充信息" without specifying what information, or options that all say roughly the same thing with different labels. If a blocker has only one valid resolution, state it as the single recommended action — do not fabricate false choices to reach a 2-option minimum.
   - When escalating a repeated blocker, write the decision package back into the current feature docs so later runs can reuse one stable entry point. The stable writeback target is `specs/<feature>/memory/open-items.md`; if `prd.md` or `spec-outline.md` already carries the blocker decision, keep the same `blocker-signature` and route there instead of inventing a new one.
   - New evidence means only user confirmation, recovered source, explicit rebase decision, feature split result, risk/compliance/owner decision, or document evidence that can change readiness. Rewording, template completion, and model re-summarization do not count.
   - For high-risk, 0-to-1 product direction, scope split, source rebase, governance candidate, real money/data, compliance, or irreversible-impact cases, `READY_FOR_SPECIFY` still requires an explicit `Owner Review Required` prompt in `Outline Decision` or `Handoff To Specify` before suggesting `/sp.specify`.
   - The `Owner Review Required` block must include `Risk Type`, `Review Focus`, `Impact If Approved`, `Impact If Rejected`, `Recommended Choice`, and `Confirm To Proceed`.
7. Generate and consume the graphical Outline confirmation.
   - Before generation, verify that the installed discovery schemas, renderer modules, or launcher support are present. If installed discovery schemas, renderer modules, or launcher support are missing, explain that already initialized projects do not receive new template assets automatically and tell the user to run `specify init --force` from the target project before retrying.
   - Generate `specs/<feature>/prd/review/outline-review-data.json` from the current `spec-outline.md` using the installed Outline schema. Keep the three bounded views focused on product intent, scope/coverage, and readiness; do not introduce Flow, UI, API, database, or implementation design.
   - Give every review generation a stable Review Data ID. After writing the complete review JSON, compute it with `.specify/review/scripts/review-data-id.mjs`; never invent or preserve the ID after changing any review field. Compute the canonical Outline digest separately with `.specify/review/scripts/outline-digest.mjs`, passing the exact source authority IDs, and record an `Outline Confirmation` block in `spec-outline.md` with `Contract Version`, `Review Data`, `Review Data ID`, `Outline Digest`, `Source Authority IDs`, and `Confirmation`.
   - Validate the data, then launch the fixed renderer with `node .specify/review/scripts/serve-review.mjs --outline <feature>` and relay its verified URL. The launcher defaults to `127.0.0.1`; for a trusted LAN or Tailscale network, an operator may explicitly add `--host <RFC1918-or-Tailscale-ip>` (RFC1918 or `100.64.0.0/10`) and the command must relay that exact emitted URL. Never substitute `0.0.0.0`, a public address, hostname, guessed host, or guessed port. LAN/Tailscale mode warns that reachable devices may read or submit the current session, so stop the launcher after review. If a browser cannot be launched, provide the URL and keep the status pending.
   - Browser state, localStorage, preview completion, local writeback, or download alone never authorizes `/sp.specify`. The loopback writer mechanically records the complete result at `specs/<feature>/prd/review/outline-confirmation.md`; it does not call a model or revise the Outline. A fully confirmed write returns `--consume-review-confirmation`, which validates the still-active current identity without regeneration. A normal `/sp.prd` instead runs the reset choice; preserved archives are review input only and can never authorize regenerated output.
   - A prior `outline-confirmation.md` is handled by the command-artifact reset choice before generation. In preserve mode, validate its identity and use `revision_requests` and old decisions only as non-authoritative candidates while regenerating the complete current Outline and complete fresh review set. In clear mode, do not read or reconstruct them. A revision request is an instruction to reconsider, never authorization.
   - When the current `outline-confirmation.md` has `human_confirmation: CONFIRMED`, matching identities, no needs-decision, unresolved, draft-excluded, or revision-request items, and current owner approval, treat that git-trackable document as the verified authorization record. Only then change the current decision from `AWAITING_OUTLINE_CONFIRMATION` to `READY_FOR_SPECIFY`, set the next route to `/sp.specify`, and append the transition to `Status History`. A downloaded package or copied summary may be consumed only as an explicit fallback when local writer delivery failed with `allow_fallback: true`; identity, target-version, validation, permission, and request-ID conflicts require a fresh review instead.
   - Any change to the digest-bearing outline content or Source Authority IDs invalidates the old confirmation. Regenerate the review, return to `AWAITING_OUTLINE_CONFIRMATION`, and require fresh confirmation rather than editing identity fields to match.
8. Handle constitution-related findings without mixing command ownership.
   - Governance-like material belongs in `.specify/memory/constitution.md` as a `Constitution Candidate` when it may apply across features or affects safety, compliance, irreversible operations, real money, real data, long-term engineering discipline, verification gates, or human decision rules.
   - `/sp.prd` may only append or update the `Constitution Candidates` section.
   - It must not rewrite formal constitution rules, stage boundaries, validation discipline, or project governance text.
   - Candidate status values are fixed: `proposed`, `under-review`, `promoted`, `rejected`, `merged`.
   - Candidates do not override formal constitution rules.
   - Single-feature local risks, todos, and requirement tradeoffs belong in `prd.md`, feature memory, or `open-items.md`, not the constitution candidate section.
9. Refresh lightweight memory only when it prevents later rediscovery.
   - Create or update `specs/<feature>/memory/open-items.md` for unresolved high-impact questions, risks, blockers, or decisions.
   - Do not duplicate the full PRD into memory.
   - Record only routing summaries, open decisions, PRD path, outline path, outline readiness status, and stable handoff pointers.

   - Confirm `Handoff To Specify` summarizes what `/sp.specify` should stabilize when ready; when not ready, it must point to the same next route as `Outline Decision` and must not create a second conflicting decision.

## Key Rules

- `prd.md` may contain drafts, but its user-confirmed, formally sourced, and consumed-decision content is authoritative requirement input; never discard those facts when regenerating Outline.
- Do not skip `/sp.prd` for new feature work. Keep it lean for clear requirements rather than bypassing it.
- Do not let `spec-outline.md` replace `/sp.specify`, `/sp.flow`, `/sp.ui`, `/sp.plan`, or `/sp.tasks`.
- Do not mark a blocking `spec-outline.md` as `READY_FOR_SPECIFY`.
- Do not treat browser state, localStorage, preview completion, local writeback by itself, or a downloaded file by itself as authorization.
- Do not omit `Outline Decision` when key PRD uncertainty blocks stable outline readiness.
- Do not leave a clear feature directory without a blocking `spec-outline.md` when downstream commands need a predictable blocker entry point.
- Do not loop on the same unchanged outline blocker; escalate to `BLOCKED` or `NEEDS_DECISION`.
- Do not move high-risk or source-rebase outlines downstream without an explicit owner review prompt.
- Do not let PRD detail grow into implementation design.
- Do not promote `[src:ai-proposed]` content without user confirmation.
- Do not treat candidate subprojects as approved boundaries before a validated user response records `Project Decomposition`.
- Do not send a confirmed decomposed parent product to `/sp.specify`; use each `Subproject Handoff` to start the child-level PRD and Outline process.
- Do not bypass `/sp.specify`. Stable requirements still belong in `spec.md`.
- Do not rewrite formal constitution content from `/sp.prd`; use `Constitution Candidates` only.
- If PRD discovery finds a new independent business goal, role, workflow, acceptance boundary, release scope, or scope fork, do not route directly to `/sp.specify`. At any tree depth, encode product-boundary choices in graphical Discovery and wait for its response; otherwise keep or set `spec-outline.md` to `SPLIT_REQUIRED`, `NEEDS_CLARIFY`, `NEEDS_SOURCE`, `NEEDS_DECISION`, or `BLOCKED`, then route to another `/sp.prd` pass, source recovery, owner decision, feature split confirmation, or `/sp.clarify` only when the decision cannot be represented by Discovery.
- If PRD discovery finds unclear product intent, risk acceptance, governance tradeoff, or another high-impact human choice, first classify whether it changes a project boundary or capability ownership at any tree depth. If it does, encode the choice in graphical Discovery and keep `NEXT_COMMAND_EXEC: None`; otherwise route the focused non-boundary choice to `/sp.clarify` with a plain-language decision package when the node-bound Discovery contract cannot express it.

## Next

End every run with a concrete closeout recommendation. Do not only list readiness branches. Give 2-3 options, choose one, explain why, and provide a one-line copy-pasteable `NEXT_COMMAND`.

Before choosing the recommendation, reconcile `.specify/memory/active-context.md`, `.specify/memory/feature-map.md`, feature `memory/index.md`, feature `memory/open-items.md`, PRD evidence, `spec-outline.md` readiness, and unresolved candidate requirements. If source authority, split, or human choice evidence is missing, classify missing split or human-choice evidence before recommending a route: keep boundary and ownership choices at any tree depth in graphical Discovery with `NEXT_COMMAND_EXEC: None`; use `/sp.clarify` only for focused non-boundary decisions Discovery cannot express; otherwise recommend `/sp.prd`, source recovery, or `/sp.constitution` instead of `/sp.specify`.

If the closeout names a numbered feature, module, or mainline such as `110-template-library-template-application`, include 1-3 short Chinese sentences explaining what it mainly does and why it matters. If the role is not confirmed by current evidence, say it is not confirmed and recommend evidence repair or `/sp.route all`.

WHY_THIS_NEXT: <why this is the correct direction, grounded in global/feature memory, open-items, Stage Readiness, and this command evidence>

Command-specific guidance:
